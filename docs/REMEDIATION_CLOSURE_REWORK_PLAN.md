## 3. 阶段 A / K1：把“可能还会写”变成持久状态

### 3.1 新增最小持久模型

| 对象 | 必要字段/约束 |
|---|---|
| `IndexExecution` | execution_id、document_id、owner、space、generation、token、状态、lease_expires_at、closed_at、关闭依据/错误码；同文档代次唯一 |
| 写入目标清单 | execution_id、批次号、明确 vector_ids 或确定性 ID 区间、目标数量、批次写入状态；必须在该批外部写入前提交 |
| `CleanupTarget` | task_id、文档/代次或遗留清单引用、精确目标快照、核验游标；不能只存 MD5 或动态“比 n 小”条件 |
| 文档墓碑 | 保留删除申请及不可见性，关联尚未关闭的执行和未完成清理；不能被主记录删除级联销毁 |

执行状态建议 `prepared → writing → closed`；超时、连接断开、进程失联但外部结果不确定则 `unknown`。结果成功/失败与是否仍可能写入分开记录：失败不自动等于 closed。

清理任务增加 `waiting_writer` 或等价原因，保留 pending/claimed/failed/blocked/done。`verified_empty_at` 可作为观测字段保留，**不能再独立决定 done**。

### 3.2 明确事务和外部调用顺序

1. 领取事务：检查资源和执行状态，原子分配 generation/token，登记执行清单并提交；未提交不得写向量。
2. 每批写入前提交该批 ID 清单。所有 ID 含不可复用的 document_id 与 generation；重试同一批使用同一 ID，新执行代次使用新 ID。
3. 外部调用在 SQL 事务外执行。每次调度前检查执行权限，但这只是减少迟到写入，不能假装可以撤销已发出的请求。
4. 所有本地子任务已结束，且所有远端请求结果已明确、没有仍在执行或结果未知的写入，才能条件记录 closed。正常完成与明确失败都可以关闭；超时/取消不确定时留 unknown。
5. 正常发布事务：按 owner/document/generation/token 检查发布权限，更新 active 指针、记录执行关闭并登记旧目标清理；提交失败不清理旧 active 代次。提交结果不明时重新读取持久状态协调，不能盲目删除可能已发布的代次。
6. 删除事务：撤销发布权限、立即撤回可见性、登记墓碑及全部已知目标。若旧写入者最终结束，允许其用执行身份记录“我已关闭”，但禁止它再更新文档状态为 indexed/pending。

### 3.3 取消与失联的处理边界

- `asyncio` 取消、客户端请求超时和租约到期都不是远端停止证明；`to_thread` 的等待被取消也不等于线程终止。
- 保存实际写调用的任务句柄，由执行生命周期监督其结束；不能在最外层 finally 无条件写 closed。跟踪所有并发批次，不只最后一次调用。
- 进程崩溃后由协调任务发现 open/unknown 执行。没有可信的远端请求完成证明，就保持待核验并告警；可继续幂等精确清理，但不能最终销毁依据。
- 人工关闭 unknown 必须有维护窗口、写入口停止、旧进程/远端请求已排空等实际证据，记录操作理由和范围。不能让管理员仅点击“强制完成”绕过数据安全条件。

### 3.4 删除完成条件

同时满足：资源仍处于删除协议下；所有关联写入者已确定关闭；全部已知目标清理并核验为空；遗留目标无未解释项；MD5 辅助记录及文件等子任务按保留语义完成。之后才可返回彻底完成或按策略归档墓碑。

写入者未关闭时，HTTP/SSE 返回处理中而不是完成；保留既有兼容字段，新增内部状态到外部状态的明确映射。不能靠延长 60 秒窗口达到完成条件。

**验收：**旧 worker 在两次查空之后才写入，任务仍不得 done；写入结束后可最终收敛。取消线程、远端成功但确认丢失、提交失败、进程失联四种情况均有测试。引用模式见 §2.1 公共执行器和发布失败测试。

## 4. 阶段 B / K2：所有清理路径使用同一精确目标

### 4.1 三条路径一次收编

1. 同步删除取消直接 owner+MD5 删除，改为登记/处理 `CleanupTarget`。若提供快速清理，也必须调用公共目标执行函数，不再写一份过滤器。
2. document_deleted 按明确文档身份和该文档清单执行；删除后重建是新的 document_id，旧任务不能包含它。
3. superseded_generation 保存具体旧代次目标列表，而不是执行时按 owner+MD5+generation<n 扩大范围。核对目标不为当前 active；若出现冲突，暂停并协调，不能继续删。
4. v1 ID 改成包含 document_id 的统一格式；只增加 metadata 不足以隔离 ID 冲突。v1 领取/发布也必须按已分配的 document_id，而不是再按 MD5 重新查找资源。
5. 同步删除、队列重试、批删、旧文件名/MD5 删除入口使用同一目标解析和执行服务；保留 `delete_documents=False` 等原契约，不扩大删除范围。

### 4.2 遗留数据不再使用“暂时没别的文档”推断归属

- 只读分页盘点实际 ID 和 metadata。区分旧固定 ID、旧 MD5 代次 ID、随机 ID；为能够唯一归属的目标保存精确 ID 清单。
- 当前 `legacy_chunk_count` 仅在有证据证明其对应原始固定 ID 数量时使用；当前代次块数不能推断所有历史块数。
- 多资源共享/归属不清的记录进入 unresolved 清单；不按 MD5 全删、不静默跳过后标 done。
- 历史 ID 可能被旧写入者复用时，先停旧写入者并完成映射；新写入启用全新资源 ID 命名空间。否则即使保存 ID 清单，也可能删除被覆盖成新资源的数据。
- 清理及核验按有界 ID 页执行并保存进度；不要一次读取整 collection。未知返回格式按失败处理，不当成空结果。
- MD5 辅助记录和文件也须按资源归属/引用检查清理，避免向量精确了但文件仍误删。

**验收：**同用户同 MD5 的 A/B 文档及不同空间文档共存；删除 A、重建 A、清理 A 的旧代次均不影响 B。安排“查无其他文档→新资源发布→旧任务继续”交错，新资源仍完整。遗留无法映射时明确阻塞，不误标成功。实现参考 §2.1 删除编排、processor 和公共执行器。

**禁止：**“先 SQL 检查无人使用，再按 MD5 远程删除”；把 SQL 行锁当作 Chroma 请求的跨系统原子锁；全量放行缺失标识的旧向量。

## 5. 阶段 C / K3：只保留一套队列领取与回写

复制清理仓库方法的有界查询接口，将实际 worker 的领取 SQL 移入仓库后删除重复实现；worker 仅负责调度、外部调用及条件回写。

- SELECT 按 `next_retry_at, created_at, id` 取有界候选；UPDATE 对候选重新检查可领取状态、到期时间和 CLAIMED 租约过期条件。二者共用一致谓词和同一 now。
- 每次领取新 token；领取后短事务提交。所有更新包括 done、failed、blocked、verified、续租均要求 `id + token + status=claimed`，必要时检查租约。更新零行返回 lost，不伪报成功。
- 失败回写使用读取的 attempt_count 进行条件更新或原子递增，保证过期执行者不能覆盖新次数；重新发现残留或未知写入时撤销旧“查空”观测资格。
- 每项外部清理后立即短事务落结果，不在整个批次的远程执行期间持有前一项更新锁。失去租约后停止启动新清理批次；已发出的远端请求只能依靠精确、不复用目标保证重试安全。
- 超时清理的续租有上限；崩溃任务能重新领取。有限 limit、退避和 blocked 告警保留，不因持续新任务导致旧任务饿死。

**验收：**双 worker 同选候选仅一个持有有效租约；另一连接在 SELECT 后延后 next_retry_at，旧候选不得被抢领；旧 token 的所有回写均失败；超过领取上限的历史任务仍公平获得执行。复制 §2.1 fixture，真实并发必须用 MySQL 两个独立连接。

## 11.3 P1：完成 N3 取消、崩溃与提交不确定恢复

### A. 先建生命周期分支矩阵

对 v2 同步、Celery、v1 单传/多传、SSE 分别列：领取前、领取提交后、解析中、写入中、写入返回后、发布中、结束事件前。每个阶段记录执行状态、文档状态、目标 ID 是否已持久化、取消/异常由谁处理。

实施重点：

1. 将取消作为独立分支处理，不能只依赖 `except Exception`。保留取消向上层传播，不转成成功；后续数据库收尾需要独立短会话，并采用有界、受监督的收尾任务，不能无限 shield 或吞异常。
2. 实际写入线程/请求未结束时不记 closed；记录 unknown 或保留可追踪的 writing。取消 await 后仍在执行的线程要有任务句柄和最终结果监督；进程内监督不能替代持久恢复。
3. 补齐写入前持久目标：至少有执行身份、批次 ID 范围/清单和覆盖完整性。尚未建立完整清单时不得因查询无 open 行就认定全体关闭。不要为历史数据伪造 closed 记录。
4. `closed_at` 仅用于确定关闭；unknown 应留为空或使用独立观测时间。状态迁移以 execution_id/token 和允许的源状态为条件；返回零行必须作为失去所有权处理。
5. v1 发布/失败/清理使用已领取 document_id，不能在发布时再按 MD5 找另一条资源。相同内容的不同资源不得共用发布权限。
6. 保留“文档状态”与“执行状态”独立收尾：主记录缺失仍能记录自身 unknown/closed；文档处于 deleting 时不得恢复 indexed/pending。

### B. 实现崩溃恢复而不是自动假关闭

扩展现有执行表，保存可靠的租约/最后活动时间或等价存活证据，增加一个有界协调入口。租约失效只把写入者列为失联/unknown，不证明远端停止；未知执行关联的任务继续不可 done。

- 协调任务按最早待处理时间公平扫描并条件领取，不与活动执行争抢状态；处理有重试/告警，不无限扫描。
- 进程在“领取后、写入后、发布前后”退出时，重启能找到执行与目标依据。不得仅靠 Celery 消息存在与否推断远端写入完成。
- 人工解决入口复用 `resolve_unknown`，在受权限保护的运维命令中要求非空原因、操作者和证据位置，明确维护窗口/停写/排空条件；仓库函数本身不是完整运维流程。
- 未证明请求结束时保留 unknown 并告警；不能通过调大等待时间、重试次数耗尽或填写任意 reason 自动完成。

### C. 区分提交失败与提交结果不明

- **确定未提交：**保留旧 active 和恢复依据；不删除旧可见代次。
- **提交已成功但确认丢失：**重新连接并读取 document active、execution、cleanup task 的一致状态，按已提交事实恢复响应/调度；不能把已发布的新向量补偿删除。
- **暂时不能判定：**留待协调，不返回已完成。新连接读取失败也不能推断回滚。
- 发布、执行关闭、旧目标清理任务继续处于同一 SQL 事务；只在提交确认或协调证明成功后对旧目标执行清理。

### D. 必补行为测试与停点

| 场景 | 控制方式 | 硬性断言 |
|---|---|---|
| 上传取消但线程继续写 | `threading.Event` 卡住假向量调用，取消上传协程，再释放线程 | 无完成成功；未确定关闭时不 done；结束后可恢复 |
| SSE 客户端断开 | 在写入/发布边界关闭消费端 | 执行有状态依据；没有发布成功前 completed |
| 领取后进程退出 | 隔离子进程和进程间屏障 | 重启可发现执行，不能无条件 closed |
| 远端写完、确认丢失 | 假远端先保存再抛错 | unknown、目标可追踪，新资源不被误伤 |
| 发布事务回滚 | 现有 commit 失败 fixture | 旧 active 与旧向量保留 |
| commit 实际成功后抛错 | 包装 commit：真实提交后模拟连接确认丢失 | 协调读到已发布，不误补偿新代次 |
| 删除主记录后上传实际抛错 | 调用真实上传服务，不只调用 `_fail_v1_generation` | T15 的状态链和清理结果在入口层成立 |

先用隔离 fixture/屏障稳定复现；跨进程可用独立文件 SQLite 做恢复机制测试，但 MySQL 锁/事务证明留到 P4。P1 结束要求所有实际写入口有分支矩阵和通过证据，不是只新增一条方法测试。禁止 skip/xfail 关键失败。

## 11.4 P2：统一 C3 读取侧可见性

### A. 定义一份公共判定

以 `owner + document_id + active_generation` 为身份核心，结合空间授权与文档可读状态。MD5 仅用于兼容发现或内容指纹，不能作为资源主键。当前 MD5→generation 字典遇到同 MD5 多资源会丢失区分，需增加按 document_id 的批量查询接口。

读取采用两阶段：先按请求范围和权限确定候选资源/代次，再从向量库取对应数据；最终返回前检查向量身份。跨库不宣称原子快照，验收明确：删除提交后的新请求不能返回该资源；读取过程中删除发生时尽量最终复核，不能保证撤回已经发出的响应字节。

| 入口 | 具体接线与验收 |
|---|---|
| 用户知识列表 | SQL 可见资源分页后取摘要；一资源一条，不按向量代次重复；total 使用同一可见范围 |
| 文档详情 | 文件名旧接口先准确解析 owner/space/document；有歧义返回明确冲突，不任取第一个 MD5 |
| 分块列表 | 限制 active 代次、稳定块顺序与分页；当前代次缺失时不回退旧代次 |
| chunk ID 直读 | 校验 metadata owner/document/generation 与 SQL，拒绝其他用户或旧代次 |
| Agent/RAG | 公共资源身份过滤；召回不足采用有上限补召回，不无界拉全库 |
| 相关文档/笔记推荐 | 区分资源类型；知识文档走公共过滤，笔记保持自身权限规则，不混套模型 |

### B. 兼容、异常与缓存

- SQL 权限/状态查询失败时不放行原始向量；对调用方使用统一服务错误或约定的安全空结果，并可观测，不悄悄绕过校验。
- 无 document_id 的存量只经 P3 已验证映射放行；不能简单屏蔽全部历史数据就宣称兼容完成。
- 缓存键至少覆盖用户、空间及资源/代次；删除、代次切换、成员资格撤销后不能通过旧缓存绕过最终校验。
- 保留原 API 响应结构；确需新增 cursor/状态字段时补接口说明和前端适配，不顺带改路由版本。
- 列表分页、详情与块分页不能各自重写一份可见性规则；复用公共服务，避免每块一个 SQL 查询。

**验收矩阵：**每个入口覆盖本人/他人、同 MD5 不同文档、不同空间、旧代次、deleting、索引失败、合法 generation=0 存量、缺映射、权限撤销及数据库异常。新增 HTTP/服务行为测试，并复用现有前端相关接口测试。P2 可先通过新协议资源测试，但 P3 完成前兼容部分继续登记未完成，不提前全量启用严格历史过滤。

## 11.5 P3：存量映射与 dry-run 回填

### A. 盘点数据，不根据新格式猜旧数据

分页读取隔离副本或明确授权的数据源，按旧随机 ID、旧固定 ID、旧 MD5 代次 ID、新资源代次 ID 分类。每页记录 ID、必要 metadata、关联 SQL 候选、分类理由；不导出正文、密钥或不必要个人信息。

分类结果只有：可唯一映射、明确属于其他资源、无法归属、元数据损坏/冲突。无候选或多候选不能自动删除或任意归并。当前 chunk_count 不能推断所有历史固定 ID 的数量。

### B. 回填命令契约（拟新增，名称按仓库惯例）

- 默认 dry-run；写入必须显式 `--apply`，同时给出审核过的 manifest/run ID、明确 owner/space 范围和批准的数据库/collection 标识。
- 支持 batch-size、resume cursor、report path；命令启动打印脱敏目标并校验测试/业务范围，拒绝空范围隐式全库写入。
- dry-run 产出资源与块数量对账、冲突清单、拟改动摘要、输入校验摘要；没有写入 SQL/Chroma 的副作用。
- apply 逐页检查源数据仍与审核摘要一致。执行中数据变化则停止该目标并记录冲突，不能以旧映射覆盖新数据。
- 持久保存每页完成状态；重复执行幂等；中断后可续跑，不从头重复创建文档。每项改动保存 before/after 必要元数据以便审计与有限回退。

### C. 映射写入与安全切换

增加或复用持久 legacy mapping：owner、document_id、legacy ID、兼容 generation、状态、来源批次、证据摘要。generation=0 仅表示经验证的存量版本，不伪造已关闭的新执行记录。

先停旧写入者，建立映射和新 ID 命名空间，再逐批启用读取。优先保留原 ID 并通过映射读；如必须复制/更新向量身份，则先验证新副本可读，再由精确任务处理旧 ID，禁止覆盖可能被旧写入者复用的 ID。

对历史 blocked/done 任务逐个按映射重新评估。重新启用任务须保留原原因和人工/自动依据，不批量把全部 blocked 改 pending，不重放宽泛删除。未解析目标继续可见地阻塞。

**验收：**dry-run 零写；重复 apply 不增量重复；中途退出后续跑；同 MD5 跨资源不串映射；冲突保持原数据；回填后列表/详情/块数对账及真实检索通过。先在专用 collection 和临时库演练，再另获授权操作业务数据。

## 11.6 P4：真实集成、门禁与发布证据

### A. 独立环境

复用项目依赖和现有 Compose 服务，新增专用集成配置或覆盖文件：唯一 project name、专用宿主端口、独立卷、测试账号、Redis namespace 和 Chroma collection。绝不挂载业务数据目录；缺少配置直接失败，不退回生产 `.env`。

确定性 provider 仅用于功能/竞态测试，不代表真实模型质量验收；测试开关不能在生产配置默默启用。初始化、服务健康检查、测试、报告、回收按明确阶段执行，失败保留必要脱敏证据。删除卷/临时库前再次确认是本次创建的精确目标。

当前原 Compose 有固定 `notebook-*` 容器名和宿主端口，仅加 `-p` 不足以隔离；优先独立集成 Compose，若使用覆盖文件必须检查最终解析配置确已移除冲突。Chroma 按项目现有嵌入式持久目录模式验真，不臆造已有 HTTP 服务。现有 fullstack 启动列表未包含 Beat，本批要覆盖定时清理/回收需显式启动 Beat 或测试指定任务接线。复用 `front/playwright.full.config.js` 的 E2E_BASE_URL、专用账号与失败 trace；functional 的内存数据库/桩测试不能替代这层证据。

### B. 测试层级与证据

| 层级 | 必验内容 |
|---|---|
| MySQL | 实际版本；空库/存量迁移；双连接领取与删除竞态；心跳刷新后不误回收；发布原子性；危险回退拒绝 |
| Chroma | 实际 add/get/delete；线程迟到写；明确 ID/metadata 清理；同 MD5 A/B；g2 清理不伤 B 的 g1；遗留映射 |
| 全栈 | 每个上传入口→列表/详情/检索→重传→删除→不可见；SSE 失败无完成成功；权限撤销后缓存不泄漏 |
| 恢复 | worker 退出、重启、unknown 协调、部分清理恢复、回填中断；区分自动可恢复和必须人工核验 |
| 门禁 | 当前最终 SHA 后端连续两次全量、functional、Ruff、mypy、原覆盖率门禁；前端与 Django 的当前版本门禁 |

本地真实集成不依赖推送。远程 CI 在用户授权推送后运行，保存同一 SHA 的运行链接和产物；不自动推送。测试名称、命令、环境版本、实际结果和缺失项全部记录，不只填总数。

## 11.7 实施顺序、提交边界与最终完成清单

推荐执行顺序：P1 生命周期失败用例→最小实现修复→P2 新资源读取→P3 盘点工具和兼容映射→P2/P3 联合验收→P4 真实集成。只在必要时追加迁移，编号以执行时 Alembic head 为准；不修改已部署迁移来假装新增字段已存在。

每个实现批次应同时带行为测试和交付记录。发现既有协议缺口可在其所属批次内修复，不另开无边界重构；若新增外部依赖/迁移风险超出本节，先说明并获得方向。

- [ ] P1：取消、崩溃、提交结果不明均可保留依据并安全协调；所有写入口实际接线验证。
- [ ] P2：所有读取入口和缓存按资源/代次/权限过滤，既有 API 契约保持。
- [ ] P3：存量映射可审计、dry-run 无副作用、apply 幂等可恢复；未解析项明确登记。
- [ ] P4：真实服务及当前 SHA 门禁产物齐全；关键测试无 skip/xfail 掩盖。
- [ ] 原方案 R/C/K 未完成项逐条核对，不能因本节结束自动划勾。

最小阶段停点可以是“P1 完成、P2/P3/P4 未完成”，不能称整体验收通过。任何 unknown 仍无法证明停止、未解析遗留或关键集成缺证据，都应如实登记。下一次汇报区分“代码实现”“组件测试”“真实集成”“当前 SHA CI”，不再用单测全绿概括整个项目安全性。
