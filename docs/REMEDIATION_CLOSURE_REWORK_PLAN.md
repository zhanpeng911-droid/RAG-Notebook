## 3. 阶段 A / K1：把“可能还会写”变成持久状态

### 3.1 新增最小持久模型

| 对象 | 必要字段/约束 |
|---|---|
| `IndexExecution` | execution_id、document_id、owner、space、generation、token、状态、lease_expires_at、closed_at、关闭依据/错误码；同文档代次唯一 |
| 写入目标清单 | execution_id、批次号、明确 vector_ids 或确定性 ID 区间、目标数量、批次写入状态；必须在该批外部写入前提交 |
| `CleanupTarget` | task_id、文档/代次或遗留清单引用、精确目标快照、核验游标；不能只存 MD5 或动态“比 n 小”条件 |
| 文档墓碑 | 保留删除申请及不可见性，关联尚未关闭的执行和未完成清理；不能被主记录删除级联销毁 |

执行状态建议 `prepared → writing → closed`；超时、连接断开、进程失联但外部结果不确定则 `unknown`。结果成功/失败与是否仍可能写入分开记录：失败不自动等于 closed。

清理任务增加 `waiting_writer` 或等价原因，保留 pending/claimed/failed/blocked/done。`verified_empty_at` 可作为观测字段保留，**不能再独立决定 done**。

### 3.2 明确事务和外部调用顺序

1. 领取事务：检查资源和执行状态，原子分配 generation/token，登记执行清单并提交；未提交不得写向量。
2. 每批写入前提交该批 ID 清单。所有 ID 含不可复用的 document_id 与 generation；重试同一批使用同一 ID，新执行代次使用新 ID。
3. 外部调用在 SQL 事务外执行。每次调度前检查执行权限，但这只是减少迟到写入，不能假装可以撤销已发出的请求。
4. 所有本地子任务已结束，且所有远端请求结果已明确、没有仍在执行或结果未知的写入，才能条件记录 closed。正常完成与明确失败都可以关闭；超时/取消不确定时留 unknown。
5. 正常发布事务：按 owner/document/generation/token 检查发布权限，更新 active 指针、记录执行关闭并登记旧目标清理；提交失败不清理旧 active 代次。提交结果不明时重新读取持久状态协调，不能盲目删除可能已发布的代次。
6. 删除事务：撤销发布权限、立即撤回可见性、登记墓碑及全部已知目标。若旧写入者最终结束，允许其用执行身份记录“我已关闭”，但禁止它再更新文档状态为 indexed/pending。

### 3.3 取消与失联的处理边界

- `asyncio` 取消、客户端请求超时和租约到期都不是远端停止证明；`to_thread` 的等待被取消也不等于线程终止。
- 保存实际写调用的任务句柄，由执行生命周期监督其结束；不能在最外层 finally 无条件写 closed。跟踪所有并发批次，不只最后一次调用。
- 进程崩溃后由协调任务发现 open/unknown 执行。没有可信的远端请求完成证明，就保持待核验并告警；可继续幂等精确清理，但不能最终销毁依据。
- 人工关闭 unknown 必须有维护窗口、写入口停止、旧进程/远端请求已排空等实际证据，记录操作理由和范围。不能让管理员仅点击“强制完成”绕过数据安全条件。

### 3.4 删除完成条件

同时满足：资源仍处于删除协议下；所有关联写入者已确定关闭；全部已知目标清理并核验为空；遗留目标无未解释项；MD5 辅助记录及文件等子任务按保留语义完成。之后才可返回彻底完成或按策略归档墓碑。

写入者未关闭时，HTTP/SSE 返回处理中而不是完成；保留既有兼容字段，新增内部状态到外部状态的明确映射。不能靠延长 60 秒窗口达到完成条件。

**验收：**旧 worker 在两次查空之后才写入，任务仍不得 done；写入结束后可最终收敛。取消线程、远端成功但确认丢失、提交失败、进程失联四种情况均有测试。引用模式见 §2.1 公共执行器和发布失败测试。

## 4. 阶段 B / K2：所有清理路径使用同一精确目标

### 4.1 三条路径一次收编

1. 同步删除取消直接 owner+MD5 删除，改为登记/处理 `CleanupTarget`。若提供快速清理，也必须调用公共目标执行函数，不再写一份过滤器。
2. document_deleted 按明确文档身份和该文档清单执行；删除后重建是新的 document_id，旧任务不能包含它。
3. superseded_generation 保存具体旧代次目标列表，而不是执行时按 owner+MD5+generation<n 扩大范围。核对目标不为当前 active；若出现冲突，暂停并协调，不能继续删。
4. v1 ID 改成包含 document_id 的统一格式；只增加 metadata 不足以隔离 ID 冲突。v1 领取/发布也必须按已分配的 document_id，而不是再按 MD5 重新查找资源。
5. 同步删除、队列重试、批删、旧文件名/MD5 删除入口使用同一目标解析和执行服务；保留 `delete_documents=False` 等原契约，不扩大删除范围。

### 4.2 遗留数据不再使用“暂时没别的文档”推断归属

- 只读分页盘点实际 ID 和 metadata。区分旧固定 ID、旧 MD5 代次 ID、随机 ID；为能够唯一归属的目标保存精确 ID 清单。
- 当前 `legacy_chunk_count` 仅在有证据证明其对应原始固定 ID 数量时使用；当前代次块数不能推断所有历史块数。
- 多资源共享/归属不清的记录进入 unresolved 清单；不按 MD5 全删、不静默跳过后标 done。
- 历史 ID 可能被旧写入者复用时，先停旧写入者并完成映射；新写入启用全新资源 ID 命名空间。否则即使保存 ID 清单，也可能删除被覆盖成新资源的数据。
- 清理及核验按有界 ID 页执行并保存进度；不要一次读取整 collection。未知返回格式按失败处理，不当成空结果。
- MD5 辅助记录和文件也须按资源归属/引用检查清理，避免向量精确了但文件仍误删。

**验收：**同用户同 MD5 的 A/B 文档及不同空间文档共存；删除 A、重建 A、清理 A 的旧代次均不影响 B。安排“查无其他文档→新资源发布→旧任务继续”交错，新资源仍完整。遗留无法映射时明确阻塞，不误标成功。实现参考 §2.1 删除编排、processor 和公共执行器。

**禁止：**“先 SQL 检查无人使用，再按 MD5 远程删除”；把 SQL 行锁当作 Chroma 请求的跨系统原子锁；全量放行缺失标识的旧向量。

## 5. 阶段 C / K3：只保留一套队列领取与回写

复制清理仓库方法的有界查询接口，将实际 worker 的领取 SQL 移入仓库后删除重复实现；worker 仅负责调度、外部调用及条件回写。

- SELECT 按 `next_retry_at, created_at, id` 取有界候选；UPDATE 对候选重新检查可领取状态、到期时间和 CLAIMED 租约过期条件。二者共用一致谓词和同一 now。
- 每次领取新 token；领取后短事务提交。所有更新包括 done、failed、blocked、verified、续租均要求 `id + token + status=claimed`，必要时检查租约。更新零行返回 lost，不伪报成功。
- 失败回写使用读取的 attempt_count 进行条件更新或原子递增，保证过期执行者不能覆盖新次数；重新发现残留或未知写入时撤销旧“查空”观测资格。
- 每项外部清理后立即短事务落结果，不在整个批次的远程执行期间持有前一项更新锁。失去租约后停止启动新清理批次；已发出的远端请求只能依靠精确、不复用目标保证重试安全。
- 超时清理的续租有上限；崩溃任务能重新领取。有限 limit、退避和 blocked 告警保留，不因持续新任务导致旧任务饿死。

**验收：**双 worker 同选候选仅一个持有有效租约；另一连接在 SELECT 后延后 next_retry_at，旧候选不得被抢领；旧 token 的所有回写均失败；超过领取上限的历史任务仍公平获得执行。复制 §2.1 fixture，真实并发必须用 MySQL 两个独立连接。

### 10.2 批次 N1：校准红用例，并建立真正的关闭门回归

**实现顺序：**先保存当前测试原始失败输出，再按业务不变量修正测试前置状态，最后修实际实现。定向运行范围为 `test_closure_rework.py` 和 `test_index_delete_orchestration.py`；在隔离配置确认后运行，不读取业务连接作为默认配置。

3. **未知/缺失：**分别构造 unknown，以及没有执行记录但属于未纳管入口/历史数据的任务。两者都不得凭 `has_open_executions == false` 当作已证明安全。已有且覆盖完整的 closed 清单则应能正常完成，避免永久阻塞所有清理。

**验证门槛：**每个用例都断言前置 SQL 状态、实际向量内容、最终任务状态；不能只断言调用次数。确需验证退避的测试通过虚拟时钟跨过 next_retry_at；连续立即调用 worker 不代表经历了多轮重试。禁止把这些用例改成 skip/xfail 来恢复全绿。

### 10.3 批次 N2：补齐 K3，优先解决队列所有权

复制现有 `claim_due_tasks` 的第一阶段谓词到公共构造方法，第二阶段 UPDATE 必须再次检查：可领取状态、next_retry_at 已到期、claimed 的租约已过期。两阶段使用相同 now；仍采用有界 ID 列表，不恢复 MySQL 不支持的子查询形式。

### 10.4 批次 N3：K1 从“有表”补到“完整覆盖”

以现有 `DocumentIndexExecution` 为唯一执行模型，完成下面三件事：

1. **覆盖证明：**建立每个清理目标对应哪些执行/批次的明确关联，并标明清单是否完整。新协议在领取事务就登记；历史和未纳管入口标记待映射。无记录默认不能推断为全部关闭，也不能伪造 closed 行来消除阻塞。
2. **关闭可信：**检查缺文件、空文档、空切片、发布拒绝、提交失败、异常、取消及崩溃路径。明确没有发出写入可直接关闭；已发出写入但结果未知保留 unknown。取消 await 不代表线程停了；关闭接口不能无条件覆盖已确认的 closed，也不能以迟到回调修改新执行身份。
3. **完成次序：**确认关联写入者关闭之后，再做最终精确清理/核验，随后条件标 done。不能先查空、旧写入者写完并关闭、再只查关闭状态就 done；那会把最后一次迟到写入留在两次检查之间。中途允许预清理，但预清理查空不是最终证据。

发布只允许当前 owner/document/generation/token；执行清单中的 token 必须真正参与发布/失败/关闭条件，而不是只存字段。删除撤销后，旧执行只可记录自身关闭，不得重置文档状态。任务完成只依赖其关联目标执行；不能因为无关新代次持续索引就永久阻塞安全的旧代次回收。

已定位的具体分支应优先补回归：执行器切片为空的两个返回、加载为空且条件失败的返回均检查是否遗留 writing；现有 `close_execution` 只允许 writing 转换，须增加有审计依据的 unknown 解决路径。unknown 不能填写代表确定关闭的 closed_at，应使用独立异常观测时间或保留为空。复用并集中现有执行仓库职责，不维持两份不同含义的 has_open_executions。

**验收：**writing、unknown、缺清单、全部 closed 四类分支；取消后线程仍写；查询为空后旧写入完成并关闭；失败未发布的部分写入也有清理目标。调用实际公共执行器，并保存目标 ID，不能只手工设置状态替代全部生命周期测试。
