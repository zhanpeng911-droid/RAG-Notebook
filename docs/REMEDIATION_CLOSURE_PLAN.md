## 1. 目标与结论

本轮主要是**正确性、数据一致性和可恢复性整改**，不是界面美化或单纯性能优化。目标是保证：删除不被旧任务复活、只有已发布代次可见、失败清理不会丢失、运行回收能够在实际 MySQL 上执行。

### 2.2 先冻结四条业务契约

## 3. 总体设计：一套执行协议，三类持久记录

```text
v1 单传 / 多传 / SSE / v2 同步 / Celery
                 ↓ 入口适配、校验、文件落盘
       公共领取事务：代次 + 令牌 + 执行清单
                 ↓ 事务外分块写向量
       条件发布事务：active 指针 + 清理任务
                 ↓ 提交成功
       统一可见性过滤       持久清理 worker
```

### 3.1 数据模型

| 记录 | 建议字段与约束 | 作用 |
|---|---|---|
| 文档主记录（扩展现有） | 保留 generation/active_generation；增加执行令牌、执行租约、删除申请时间（若不存在） | 当前资源状态与唯一发布权限 |
| 代次执行清单（新增） | `(document_id, generation)` 唯一；owner、space、token、writer 状态、预期块数、向量 ID 规则或分页 ID 清单、创建/关闭时间 | 在外部写入之前留下可恢复意图，记录失败、旧代次及旧格式向量 |
| 清理任务（新增） | 文档/代次/遗留清单引用、原因、状态、attempt_count、next_retry_at、claim_token、lease_expires_at、最后错误、核验时间；清理目标唯一 | 公平领取、失败重试、崩溃恢复、删除后仍可继续清理 |

删除墓碑可以保留在文档主记录，也可独立保存；**不得因主记录物理删除而级联删除未完成的清单和清理任务**。不存正文或敏感错误内容；为到期任务领取、文档代次查询建立索引。

迁移号由实施时真实 Alembic head 决定。009 已部署的情况下只追加迁移，不修改 008/009 历史升级脚本来假装新字段已存在。

### 3.2 状态与事务不变量

- 领取只允许可执行状态，并在一个短事务内原子递增 generation、生成 token、插入执行清单；`deleting` 永不允许领取。
- 重试只能条件修改本次持有的 generation/token；失败回调不能覆盖删除状态或新执行者状态。
- 发布必须同时满足 owner、文档状态、generation、token；更新 active 指针与创建旧代次清理任务在同一事务提交。
- 事务外执行文件、模型、Chroma 网络调用；禁止持有 SQL 行锁等待 embedding 或远程清理。
- 删除事务撤销执行权限、撤回可见性、保存墓碑和清理任务；之后才做远程删除。
- 发布失败、提交结果不确定、进程崩溃都保留执行清单，由协调任务核对实际提交状态后补偿；不能立即按猜测删除可能已发布的代次。
- 对同一资源采用一致锁顺序。涉及会话父子记录时沿用父会话先锁、运行/反馈后锁，避免新逻辑引入反向锁序。

## 4. 阶段 A：C1——堵住复活并统一执行身份

### 实施内容

1. 复制现有仓库条件领取/发布模式，先给 v1 增加拒绝 `deleting`、拒绝抢占 `indexing` 的条件更新；并发领取以受影响行数判断结果，不用“先读后赋值”。这一补丁可单独验收，但不能标为全入口完成。
2. 新增统一 `PreparedDocument` 准备过程：校验内容、增量计算 MD5、受限分块落盘、得到明确文件路径。复用现有大小限制，消除重复整文件读取、`chunks` 拼接和失败时从 EOF 再读文件的依赖。
3. v1 保留参数与响应适配，取消其独立状态分配/发布逻辑，转调公共执行器；保证重试拿到真实持久文件，不能登记 `file_path=""` 却承诺可后台重试。
4. 公共执行结果区分 `published / busy / cancelled_by_delete / failed` 等内部结果。仅 `published` 且提交成功可转成旧接口的完成成功；条件发布被拒必须向上层传播。
5. 与新增执行清单一起接入 generation/token。ID 必须包含稳定资源身份和代次；对旧 ID 通过清单兼容，不能只统一新 ID 字符串而丢失旧数据。

### 验收清单

- 已是 deleting 的 v1 请求：状态、代次不变，向量写入为零。
- 两个独立 MySQL 连接同时领取：只有一个成功，不产生相同代次的双执行者。
- 领取后删除获胜，旧执行者成功或失败回调均不能发布、重置 pending 或返回完成成功。
- 相同 MD5、不同 owner/space/document 的上传和清理互不影响。
- 发布提交失败保留旧代次，旧向量删除为零；提交成功后才生成可执行的旧代次清理工作。

**防走偏：**不再增加第三套 v1 状态机；不把 404/409 都吞成上传成功；不以单测 patch 新函数就宣称真实入口已接入。

## 5. 阶段 B：C2——MySQL 兼容回收与独立心跳

本阶段与索引改造相对独立，可独立提交。沿用 `reclaim_stale_runs` 的返回行数契约。

### 实施内容

1. 第一条 SELECT 按过期租约筛选，`ORDER BY created_at, id`，应用经校验的 limit，取回实际 ID 列表；空列表直接返回 0。
2. 第二条 UPDATE 使用上述有界 ID 列表，**再次同时检查** `status=started` 和 `COALESCE(heartbeat_at, created_at) < cutoff`，再写 timeout。不能把带 LIMIT 的 SELECT 继续嵌入 IN。
3. limit 必须为正数且有上限；使用同一 cutoff。重复回收幂等；并发心跳或终态提交获胜时 UPDATE 行数减少是正常结果，不无限补扫。
4. 心跳由运行生命周期管理的独立异步任务按间隔发送，不依赖 SSE 恰好产生事件。非流式运行同样覆盖；每次用独立短会话，不跨任务共享 AsyncSession。
5. 心跳只更新 still-started 的运行，完成/取消时在 finally 中停止并 await 心跳任务；异常有日志和指标。心跳周期、租约期限和容忍间隔明确配置，不能把运行总时限等同于心跳租约。

### 验收清单

- MySQL 8.0.12 临时库执行真实仓库方法：无 1235 错误，limit=1 最多回收一条，顺序确定。
- SELECT 后另一连接刷新心跳：该运行不被 UPDATE 回收；改终态亦不被覆盖。
- 两个回收 worker 同时执行：无重复终态副作用；第二次回收收敛。
- provider 长时间不产出 SSE 事件：心跳仍更新，不误回收；进程停止心跳后，超过租约可被回收。
- 限额、空结果、时区、取消清理均有行为测试。SQLite 测试及 SQL 源码断言不能替代 MySQL 验收。

## 6. 阶段 C：C3——全入口接入与存量兼容

### 实施内容与入口矩阵

先复制公共执行器与读取过滤模式，再逐项接线；实施者在 PR 中将下表补为具体路由、服务方法和行为测试名。

| 范围 | 必须覆盖 |
|---|---|
| 写入 | v1 single、multiple、multiple/stream；v2 同步、后台 worker、重试；笔记向量同步单独核对其资源类型 |
| 读取 | Agent/RAG 检索、相关文档推荐、用户知识列表、文档详情、分块列表、按 chunk ID 读取；缓存命中也不得绕过权限/代次规则 |
| 删除 | 文档 ID、旧文件名/MD5 入口、批量删除、按用户/空间清理，全部接公共删除协议 |

1. 收编 `_process_slice_results` 的直接 `add_documents` 路径。SSE 可以报告解析/分块进度，但不能在公共发布成功前发送成功终态。
2. 建立公共可见性判定：owner 和空间权限通过、资源允许读取、向量对应 SQL 当前 active 代次。详情/分块/列表不直接把原始 Chroma 结果返回用户。
3. 列表按资源聚合和分页，不把不同代次重复显示为多份文档；不以整 collection 拉取代替有界查询。正常检索中若先召回后过滤导致不足，采用有界补召回并设置上限。
4. 盘点三类历史向量：旧随机 ID、旧固定 v1 ID、当前带代次 ID。生成只读映射报告，再按 owner、空间、资源身份建立 generation=0 的兼容清单；不能只按 MD5 合并。
5. 已完成映射的纯存量文档允许按显式 generation=0 清单读取；已发布新代次时屏蔽旧代次。无法映射的记录进入隔离待处理清单，不静默删除，也不全量放行缺失标识的数据。
6. 兼容回填采用可重入、小批次、保存游标和统计的管理命令；先 dry-run，再在维护窗口执行。回填结束和入口接线完成之前，不宣称“全栈统一”。

### 验收清单

- 每个上传入口新建文档后均可检索；重传从 N 块变 M 块，不出现旧尾块或重复可见块。
- 每个读取入口拒绝他人、已删除、旧代次及缺失必要身份的数据；授权存量仍可访问。
- 相同内容跨空间不串数据；已撤销空间权限的缓存命中不能返回内容。
- 删除与流式写入交错时无虚假完成事件；所有删除入口保留原参数语义。
- 静态扫描直写/直读点逐一归类，允许列表必须有理由；“搜不到某字符串”只能辅助，不能代替调用真实路由的测试。

## 7. 阶段 D：C4——持久、公平、可证明的清理

### 实施内容

1. 以清理任务表为主队列，取最早到期任务，按 `next_retry_at, created_at, id` 有界领取；条件写 claim_token 和租约，清理在事务外执行。不得继续只扫描最近 50 条 indexed 文档。
2. 删除按 owner + document + generation 或明确的旧 ID 清单定位。清理前核对目标不是当前可见代次；不拿过期 active 快照做宽泛的 MD5 删除，避免误删同内容新资源。
3. 成功、失败、部分成功分别记录；远程异常不能被内部吞掉后计为成功。失败指数退避并有上限告警；达到重试阈值进入人工可见的 blocked，而不是删除任务记录。
4. worker 崩溃后租约到期可再领；远端删除成功但确认丢失时重试幂等。旧记录巡检采用持久游标，仅作队列漏单的补充，不代替任务表。
5. 删除后保留墓碑、写入清单及任务，覆盖“SQL 删除后旧 worker 才写入”的窗口。最终清理包括向量、MD5 辅助记录、文件，但共享资源须先核对引用，不按 MD5 盲删。
6. 清理完成要求：写入者已确定关闭，已知目标按有界 ID 查询核验为空，所有子任务成功。**租约过期不等于旧线程或远程请求已停止**；结果不确定的写入者保留 unknown/待核验状态，持续补偿或维护窗口处理，不能以一次查询为空宣称彻底完成。
7. 墓碑和清单保留期由运营策略配置；未完成或存在未知写入者的记录不可按时间自动物理删除。已完成记录归档后才讨论保留期清理。

### 验收清单

- 删除后迟到写入真实 Chroma：数据始终不可读，清理任务不丢，写入者关闭后最终为空。
- 构造超过扫描上限的旧失败任务，同时持续新增文档：旧任务仍获得执行机会，不被最新文档饿死。
- 部分删除失败、连接中断、删除成功但确认丢失、领取后杀进程：任务可恢复且不误计成功。
- 清理旧代次时新代次发布：新代次可检索且不被删除；同 MD5 的其他文档不受影响。
- 输出 pending/retry/blocked 数量、最老任务年龄、清理耗时和失败原因；日志含 document/generation/job 标识，不泄露正文或密钥。

## 8. 发布、迁移与回退

建议提交顺序：①失败回归与隔离；②C1 条件领取止血；③C2 回收与心跳；④新增清单/任务模型及迁移；⑤公共执行协议与全入口适配；⑥读取兼容回填；⑦持久清理；⑧真实集成证据与交付记录。顺序是依赖建议，不要求凑固定提交数量。

- 新增表/字段先做兼容扩展；在新写入启用前排空或暂停旧 worker，确保不存在不知道新协议的写入者。不能混跑旧 worker 写无清单向量。
- 存量先备份、dry-run、建立兼容映射，再启用严格读取；保留映射前后文档/块计数差异和抽样验证。
- 回退优先停写和功能开关，不直接 downgrade 丢弃清单。存在发布代次、未关闭写入者、未完成清理或删除墓碑时拒绝破坏性回退；仅检查 `active_generation > 0` 不足以覆盖未发布残留。
- 回退必须验证旧程序是否理解新状态和向量身份；不兼容时保持维护模式，不能用恢复旧二进制替代数据回退方案。
- 所有真实库变更、数据回填和远程推送按项目授权执行；本方案不构成操作业务库或推送的执行记录。

## 9. 最终验证与验收门槛

### 9.1 必须提交的证据包

### 9.2 交付记录格式

### 9.3 什么情况下可以验收
